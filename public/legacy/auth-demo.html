Authentication & Sessions

Learn the difference between authentication and authorization, and how sessions keep users logged in

Core Concepts

🔑 Authentication

WHO are you? Verifying user identity (login with username/password, biometric, etc.)

👤 Authorization

WHAT can you do? Determining what resources/actions an authenticated user can access

📍 Session

How does the server remember you after login? Maintains authenticated state across multiple requests

Authentication Flow (Session-Based)

1. User Submits Login
POST /login → username: alice, password: secret123

2. Server Verifies
Hash password → Compare with DB → MATCH ✓

3. Server Creates Session
Generate unique session ID: abc123def456
Store in-memory or database: {sid: abc123..., user: alice, expires: ...}

4. Set Cookie
HTTP Response header: Set-Cookie: sessionid=abc123def456; HttpOnly; Secure

5. Browser Stores Cookie
Browser remembers: sessionid=abc123def456

6. Future Requests
Browser auto-sends: Cookie: sessionid=abc123def456
Server validates session → Request authorized ✓

Session-Based vs Token-Based Auth

Aspect Sessions (Traditional) JWT Tokens (Modern)
Storage Server-side (database/memory) Client-side (token itself)
Stateless ❌ Server maintains state ✓ Server doesn't store sessions
Scalability ⚠️ Harder (need shared session store) ✓ Easier (each server can verify)
Security ✓ Very secure (server controls) ⚠️ Depends on secret key + HTTPS
Revocation ✓ Instant (delete from server) ❌ Hard (token still valid until expiry)
Use Case ✓ Web apps (traditional) ✓ APIs, mobile apps, microservices

Authentication Vulnerabilities

❌ Session Fixation

Attacker: Captures valid session ID (or guesses one)
Attacker: Tricks user into using that session
Attacker: Logs in with same session ID
Result: Attacker and user share same authenticated session
Prevention: Regenerate session ID after successful login

❌ Weak Session ID

Bad session ID: sessionid=1, 2, 3, 4... (sequential)
Bad session ID: sessionid=username_timestamp (predictable)
Attacker: Guesses next session ID → impersonates user
Prevention: Use cryptographically random session IDs (256+ bits)

❌ Session Hijacking

Attacker: Intercepts HTTP traffic (unencrypted)
Attacker: Steals session cookie from network
Attacker: Uses cookie to impersonate user
Prevention: Use HTTPS, set HttpOnly flag, set Secure flag

❌ No Logout

App closes browser but never invalidates session
Server still accepts old session ID for days/weeks
Attacker finds old session cookie → Still logged in!
Prevention: Invalidate session on logout, set appropriate expiry

Authentication Best Practices

  • ✓ Always use HTTPS (never HTTP for auth)
  • ✓ Use cryptographically random session/token IDs
  • ✓ Set HttpOnly and Secure flags on auth cookies
  • ✓ Regenerate session ID after successful login
  • ✓ Implement proper logout (invalidate session)
  • ✓ Set reasonable session timeout (30 min to 24 hours)
  • ✓ Hash and salt passwords (bcrypt, Argon2)
  • ✓ Implement rate limiting on login attempts
  • ✓ Use multi-factor authentication (MFA) for high-value accounts
  • ✓ Log authentication events for security monitoring
  • ✓ Use established libraries (don't roll your own)
