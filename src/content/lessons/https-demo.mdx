## The S Is Doing More Than You Think

You have typed a password into a login form on school Wi-Fi. Between your laptop and that server sits an access point, a switch, a router, an ISP, and a handful of networks you will never see. Over plain HTTP, every one of those hops can read what you sent. Not "could theoretically with sophisticated tooling" — read it, in plain text, the way you typed it. Your username, your password, your session cookie.

HTTPS is HTTP carried inside TLS, and it changes three things at once.

**Confidentiality.** The traffic is encrypted, so the hops in between see meaningless bytes instead of your credentials.

**Integrity.** The traffic is authenticated, so a network in the middle cannot quietly alter the page — no injected ads, no swapped download link, no modified bank account number.

**Authentication.** The server proves it holds the private key for a certificate issued to the hostname you actually typed. That is what stops someone from answering for `yourbank.com` when they are not your bank.

## The Handshake

Before any page data moves, the client and server run a handshake with one goal: end up sharing a secret key that nobody watching the exchange can derive.

The client opens with the TLS versions and cipher suites it supports. The server picks from that list and sends its **certificate**, which contains its public key and the hostnames it is valid for. The client checks that certificate — is it signed by an authority the browser trusts, is it still within its validity dates, does the hostname match what was typed, has it been revoked. If any check fails, you get a warning instead of a page.

With the certificate accepted, the two sides perform a key exchange. Modern TLS uses **ECDHE**, an ephemeral Diffie-Hellman exchange in which both parties contribute randomness and independently derive the same session key without that key ever crossing the wire. The server signs its part of the exchange with its private key, which is what proves it is the certificate's real owner rather than someone replaying a copied certificate.

From there the connection switches to symmetric encryption — AES — for everything else, because asymmetric crypto is far too slow for bulk traffic.

Ephemeral key exchange buys **forward secrecy**: the session key is discarded when the connection closes and was never derivable from the server's long-term private key. An attacker who records your traffic today and steals the server's private key next year still cannot decrypt what they captured.

## The Certificate Is an Identity Claim, Not the Encryption

This is where students consistently go wrong. The certificate does not encrypt anything. It is a signed statement from a certificate authority saying "the entity holding the matching private key controls this hostname." Encryption comes from the session key the handshake produced.

And notice how narrow that claim is. A standard domain-validated certificate proves control of a domain name. It proves nothing about who owns the business, whether the site is honest, or whether the download it offers is malware. Certificates are free and automated now, which is excellent for the web and means a padlock on a phishing page is completely routine.

<Callout type="exam">
The padlock means the channel is protected and the certificate matched the hostname. It does not mean the site is trustworthy. Expect at least one Security+ question built on a user who assumed HTTPS equals safe, and read certificate errors literally — expired, self-signed, untrusted issuer, and hostname mismatch are four distinct failures with four distinct causes.
</Callout>

## Attacks That Work Anyway

**Man-in-the-middle.** An attacker who can get the client to trust their certificate sits transparently between you and the server, decrypting, reading, and re-encrypting. Normally the browser refuses and throws a warning. It succeeds when the attacker's root certificate is already trusted — a managed corporate laptop, a compromised device, or a user who clicked through the warning.

**SSL stripping.** The clever one, because it never attacks TLS at all. You type `bank.com` without a scheme, so the browser sends a plain HTTP request first. An attacker on the path answers that request, keeps the victim on HTTP, and quietly maintains an HTTPS connection to the real server on the other side. The site works perfectly. The padlock is simply absent, and almost nobody notices its absence.

**HSTS** closes that window. The server sends a `Strict-Transport-Security` header, and from then on the browser refuses to speak plain HTTP to that domain — it upgrades the request internally before anything leaves the machine, and it will not let the user click past a certificate error. Preloading the domain into the browser's built-in HSTS list protects even the very first visit.

<Callout type="warn">
The response that makes things worse is teaching people to click through the warning. Every time an internal tool uses a self-signed certificate and staff are told to just accept it, you are training the exact behavior a real attacker needs. The habit transfers straight to the coffee shop network. Fix the certificate — internal CAs and free automated issuance both solve this — rather than normalizing the bypass. The related trap is assuming that adding HTTPS support is enough: if plain HTTP still answers and nothing redirects or sets HSTS, the downgrade path is wide open and the padlock you added is optional.
</Callout>

## Why This Matters

TLS is the security control you will touch most often, and usually as a problem: a certificate expired at 2 a.m. and took a service down, a monitoring check fails because an internal host uses a self-signed certificate, a user reports a warning that turns out to be a captive portal, an audit demands TLS 1.2 as a floor with old cipher suites disabled. Reading a certificate — issuer, subject, validity dates, subject alternative names — and knowing which handshake step a given error came from is genuinely day-one help desk and day-one security analyst work.

## Ethical Use

Intercepting, downgrading, or decrypting traffic is legitimate only on networks and systems you own or have explicit written authorization to test. Capturing other people's traffic on a shared network is illegal, and the fact that a tool makes it easy changes nothing about that.
