## Logging In Is the Easy Part

You type a password once and stay logged in for hours. HTTP has no memory — each request arrives at the server knowing nothing about the last one — so something has to carry your identity across every click after that first one.

That something is the **session**, and it is the part attackers actually go after. Getting the password check right is straightforward. Managing what happens for the next four hours is where the failures live.

Three ideas need to stay distinct:

**Authentication** is proving who you are. Password, passkey, certificate, biometric.

**Authorization** is deciding what you are allowed to do. It happens after authentication, on every request, and it is a separate question — being correctly logged in tells the server nothing about whether you may open the admin panel.

**The session** is what carries that established identity forward, usually as a token in a cookie. And here is what makes it interesting: that token *is* a credential. Anyone who has it is you, as far as the server is concerned. No password required.

## Two Ways to Remember a User

**Session-based (stateful).** The server generates a random identifier, stores the session details in its own memory or database, and hands the client the identifier in a cookie. Every subsequent request presents that identifier and the server looks it up. The token is opaque — it means nothing on its own, it is only a key into server-side state.

The advantage is control. Revocation is instant: delete the record and the session is dead on the next request. The cost is that the server must store and share that state, which takes coordination across multiple servers.

**Token-based (stateless).** The server issues a signed token — commonly a **JWT** — that carries the claims itself: who the user is, what roles they hold, when it expires. The server stores nothing. It validates the signature on each request and trusts the contents because tampering would break that signature.

The advantage is scale, which is why APIs and distributed systems favour it. The cost is revocation. There is no record to delete, so a valid token is accepted until it expires. That is why stateless tokens carry short lifetimes — minutes, not hours — paired with a longer-lived **refresh token** that *is* tracked server-side, restoring a revocation point.

One clarification that trips people up: a standard JWT is **signed, not encrypted**. The signature proves integrity and origin. Anyone holding the token can read the claims inside it, so it is not a place for anything sensitive.

## How Sessions Get Broken

**Session hijacking** — stealing a valid token. Over plain HTTP it is read straight off the wire. More commonly it is taken by XSS, since injected JavaScript can read `document.cookie` unless the cookie is `HttpOnly`. The defences are TLS everywhere, `HttpOnly`, and `Secure`.

**Session fixation** — the attacker sets the session ID *before* you log in, gets you to authenticate with it, and then uses the ID they already knew. Notice the attacker never steals anything; they planted the value in advance. The fix is one line of behaviour: issue a brand-new session identifier at every privilege change, especially login. The pre-login ID becomes worthless.

**Predictable identifiers** — sequential or timestamp-derived IDs can simply be guessed, and one valid guess is one hijacked account. Identifiers must come from a cryptographically secure random source and be long enough that guessing is hopeless.

**Broken lifecycle** — sessions that never expire, or a logout that clears the cookie in the browser without invalidating anything server-side. If the token remains valid, anyone who copied it is still logged in after the user believes they left. Logout must destroy the server-side session; on public machines that difference is the whole ballgame.

<Callout type="exam">
Fixation and hijacking are the pair most often confused: in fixation the attacker sets the identifier before authentication, in hijacking they steal one that already exists. Regenerating the session ID at login is the fixation answer. Also keep the cookie flags straight — HttpOnly blocks JavaScript access, Secure restricts the cookie to HTTPS, and SameSite limits cross-site sending and is a CSRF control.
</Callout>

## MFA and What It Actually Covers

Multi-factor authentication combines factors of different kinds — something you know, something you have, something you are — and it is the single highest-value control against stolen credentials, because a password alone stops being enough.

Its limits are worth knowing precisely. MFA protects the **login**. It does nothing for a session token stolen afterwards, because that token already represents a completed authentication — which is exactly why attackers now target session cookies rather than passwords. And not all factors are equal: SMS codes are vulnerable to SIM swapping and interception, push notifications invite fatigue attacks where a user eventually approves a prompt to make it stop, while hardware keys and passkeys built on WebAuthn resist phishing structurally because the credential is cryptographically bound to the real site's origin.

<Callout type="warn">
The response that makes things worse is treating a compromise as a password problem and forcing a password reset. The user resets, everyone relaxes, and the attacker stays logged in — because the session tokens issued before the reset are still valid, and no password is involved in presenting them. The same gap swallows MFA rollouts: enabling MFA on an account whose session was already stolen changes nothing for that session. Any credible credential-compromise response invalidates all active sessions and refresh tokens for the account, then resets the password. If your application has no way to terminate existing sessions, that is a finding worth raising before an incident makes it obvious.
</Callout>

## Why This Matters

Authentication and session handling produce a large share of real-world findings, and they sit in the OWASP Top 10 for that reason. As a defender you will review these decisions constantly — is the session ID regenerated at login, are the cookie flags set, does logout actually invalidate, how long do tokens live, can we revoke them during an incident. In incident response, "terminate all active sessions" is one of the first containment actions, and it only works if the application was built to allow it. This is also the ground floor for the AAA framework, SSO, SAML, and OAuth, all of which are variations on establishing an identity once and carrying it safely afterwards.

## Ethical Use

Test session handling only against applications you own or are authorized in writing to assess. Capturing, replaying, or forging another person's session token on a live system is unauthorized access, and it is treated as seriously as stealing a password — the fact that the token was visible on a shared network is not a defense. Practise on your own applications or on intentionally vulnerable targets built for it.
