## Your Script, Their Browser

SQL injection attacks the database. Cross-site scripting attacks the *other users*, and that difference is what makes it so useful to an attacker.

A site takes something you typed — a search term, a comment, a display name — and writes it back into a page. If it writes that text without encoding it, the browser has no way to know the text came from a stranger. It sees `<script>` in the markup and does what browsers do with script tags: it runs them.

The code now executes inside the victim's browser, on the real site, in the victim's logged-in session. It is not sandboxed away from anything. It can read the session cookie, read the page the user is looking at, read what they type next, and send all of it somewhere else. It can also act — submit a form, change an email address, initiate a transfer — and every one of those requests carries the victim's real credentials, because as far as the server is concerned the user made them.

That is the part worth sitting with. The attacker never touches the victim's password and never logs in. They borrow the session that is already open.

## Three Types, Three Delivery Methods

**Reflected XSS** lives in the request. The payload rides in a URL parameter, the server includes it in the response, and it executes immediately. Because the payload is in the link, the attacker needs the victim to click something — a phishing email, a shortened URL, a message in a chat. One user at a time, but the link points at the genuine site with a genuine certificate, which is what makes it convincing.

**Stored XSS** is worse, because it needs no lure. The payload is saved on the server — in a comment, a profile field, a support ticket, a product review — and served to everyone who loads that page. Every visitor is a victim, no click required. A stored payload in a high-traffic page compromises users continuously until someone finds it. This is how XSS worms like Samy propagated on MySpace: each infected profile infected every viewer.

**DOM-based XSS** never involves the server response at all. Client-side JavaScript reads something untrusted — `location.hash`, a query parameter, a `postMessage` — and writes it into the page with `innerHTML` or similar. The payload may sit after the `#` in a URL, which browsers never transmit. That means the server logs show nothing, server-side code review finds nothing, and a WAF inspecting requests sees nothing. The vulnerability is entirely in the front end.

## The Fix Is Contextual Output Encoding

Encode data at the moment it is written into the page. Encoded, `<script>` becomes `&lt;script&gt;` — the browser displays those characters as text and never parses them as a tag. The payload appears on screen as literal text, which is exactly what a comment containing angle brackets should do.

The word doing the work is **contextual**. The encoding required depends on where the data lands:

- **HTML body** — escape `< > & " '`
- **HTML attribute** — escape and always quote the attribute, or an unquoted value can break out with a space
- **URL parameter** — percent-encode
- **Inside JavaScript** — JavaScript string escaping, and far better, do not put untrusted data in script at all

Modern frameworks handle most of this for you. React, Angular, and Vue escape interpolated values by default, which is why XSS in those codebases usually traces to a deliberate bypass — `dangerouslySetInnerHTML`, `v-html`, `bypassSecurityTrustHtml`. Those are the lines to search for in review.

<Callout type="exam">
Match the type to its delivery: reflected needs a crafted link, stored fires for every visitor, DOM-based never reaches the server. The best-defense answer is output encoding. HttpOnly, CSP, and input validation are mitigations that limit damage — real controls, but they do not remove the vulnerability, and they are written as distractors for exactly that reason.
</Callout>

## Reducing the Blast Radius

**HttpOnly cookies.** A session cookie marked `HttpOnly` is invisible to `document.cookie`. XSS still runs, but it cannot steal the session — one of the highest-value outcomes is removed for one attribute.

**Content Security Policy.** A CSP header tells the browser which script sources are permitted. A strict policy blocks inline script entirely, which neutralizes most injected payloads even when the encoding bug exists.

**SameSite cookies.** Restricts when cookies ride along with cross-site requests, limiting what stolen or forged requests achieve.

None of these fix the bug. They are the reason a missed encoding becomes an incident report instead of a breach.

<Callout type="warn">
The response that makes things worse is sanitizing input by stripping tags. A filter that removes `<script>` is defeated by `<img src=x onerror=alert(1)>`, by `<svg onload=...>`, by encoding tricks, by nested tags that reassemble after the filter runs. The immediate payload stops working, the ticket gets closed, and the vulnerability stays open behind a false sense of safety — while the filter quietly corrupts legitimate data, so a user cannot post about the `<` operator. The deeper error is fixing this at input, where you must anticipate every dangerous string forever. Encoding at output is decidable: you know exactly where the data is going and how to neutralize it there. Store what the user actually typed; encode it when you display it.
</Callout>

## Why This Matters

XSS has sat in the OWASP Top 10 since the list existed, and it is the flaw most often reported through bug bounty programs. As a defender you will look for it in code review by finding where untrusted data reaches the page — `innerHTML`, template interpolation without escaping, framework escape hatches — and you will spot it in a WAF or proxy log as angle brackets and `onerror` in request parameters. It is also the standard pivot in a phishing chain: a reflected XSS on a trusted domain gives an attacker a genuine, correctly certificated URL to send, and that legitimacy is worth more than any amount of lookalike domain registration.

## Ethical Use

Test only against systems you own or have written authorization to assess — your own applications, or deliberately vulnerable targets such as DVWA, WebGoat, or Juice Shop. Injecting script into a site you do not control is unauthorized access, and it is prosecuted as such even when the payload is a harmless alert box and even when you intended to report it. If you find something on a live site, stop and use the operator's responsible disclosure process.
