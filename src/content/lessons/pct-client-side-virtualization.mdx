## One Computer, Several Computers

A student needs to learn Linux. They have one laptop, running Windows, which they also need for coursework. The old answer was a second partition and a reboot every time they switched. The current answer is a **virtual machine** — Linux running in a window, alongside Windows, on the same hardware, at the same time.

Nothing was added to the machine. The resources it already had were **divided**, and that division is what virtualization is.

## What a Hypervisor Does

A **hypervisor** is the software layer that carves one physical machine's CPU, memory, storage, and network into **virtual machines**, each of which believes it has a computer to itself. Each VM runs its own **guest** operating system, unaware of the others.

There are two kinds, and the distinction is simply *what is underneath the hypervisor*:

**Type 1 — bare metal.** Runs **directly on the hardware**. There is no host operating system. The hypervisor *is* what boots. This is what runs in data centres, because nothing sits between it and the hardware taking a cut.

**Type 2 — hosted.** Runs **as an application** on an existing operating system, the way any other program does. Start Windows, then start the virtualization software, then start a VM inside it. This is what a technician or student uses on a workstation — easy to install, easy to remove, and slower, because the host operating system is underneath consuming resources of its own.

The performance gap follows directly from the diagram. Type 1 has one layer between the guest and the hardware; type 2 has two, and the lower one is also busy running a desktop.

## Virtual Machines Are Not Free

The most common misunderstanding is that a VM is somehow lighter than a real machine. It is not. **Every VM consumes real RAM, real CPU time, and real disk from the host.** Nothing is manufactured — it is divided.

That has a practical consequence people run into immediately. On a laptop with 8 GB of RAM, assigning 6 GB to a VM leaves 2 GB for Windows and everything already open. The host starts swapping to disk, and because the host is swapping, the VM stalls too. Both become unusable at once, and the instinct — give the VM more memory, since it feels slow — makes it worse. **The host needs its own working share.**

Two other requirements catch people out:

**Hardware virtualization support** must be enabled in **BIOS/UEFI**. It is frequently off by default, and the symptom is VMs that refuse to start or crawl badly on hardware that should be more than adequate. It is a firmware setting, not a software one.

**Disk space** grows faster than expected, especially with snapshots.

<Callout type="exam">
The distinction A+ wants is **what sits below the hypervisor**. Type 1 runs on bare metal with no host OS and is the server answer. Type 2 runs as an application on a host OS and is the workstation answer. Also expect the resource point — a VM consumes the host's actual RAM and CPU — and the firmware point, that **virtualization support must be enabled in BIOS/UEFI** before VMs will run properly.
</Callout>

## Isolation Is the Reason

Beyond running two operating systems at once, the property that makes virtualization genuinely valuable is **isolation**. What happens inside a VM stays inside it. The guest cannot see the host's files or reach into its memory.

That makes a VM the correct place to:

- **Test software** before it goes near a production machine.
- **Open something suspicious** during analysis.
- **Practise destructive procedures** — repartitioning, registry surgery, a deliberately broken boot — without risking anything real.

**Snapshots** make this practical. A snapshot captures the VM's entire state at a moment in time, and restoring rolls it back in seconds. Break the guest completely, restore the snapshot, and it is as if nothing happened. That is why a VM plus a snapshot is the standard lab environment for anything you would not do to a real machine.

Snapshots are not backups, for the same reason as always: they live on the same host, they are tied to that VM, and they consume disk continuously while they exist.

<Callout type="warn">
The mistake with real consequences is trusting isolation while quietly dismantling it. A technician opens a hostile sample in a VM — correct — but that VM has a shared folder mapped to the host desktop for convenience and a bridged network adapter so it can reach the internet. Both are defaults people enable without thinking, and both are routes out. A shared folder is a writable path straight to the host, and ransomware will take it; a bridged adapter puts the sample on the office network alongside every other machine. Isolation is a configuration, not a guarantee. Before running anything hostile: remove shared folders, disconnect or isolate the network adapter, and take the snapshot first.
</Callout>

## Why This Matters in the Field

Virtualization is how you get a safe place to work. A technician with a VM and a snapshot can try the risky fix, see what it does, and roll back — rather than trying it on a customer's machine and hoping.

It is also the foundation under everything in the previous two lessons. Cloud providers are running enormous numbers of virtual machines on pooled hardware; understanding the hypervisor on your own laptop is understanding what is happening in their data centre, at a different scale.
