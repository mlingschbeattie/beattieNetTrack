## Modeling the Real World in Code

In procedural programming, code is a simple list of top-to-bottom instructions. That works fine for a 20-line backup script, but when you are building an enterprise system with 500,000 lines of code—like an airline reservation platform or a massive multiplayer game—procedural code turns into an unmaintainable tangle of "spaghetti code."

**Object-Oriented Programming (OOP)** is the dominant architectural paradigm used across enterprise software (Java, Python, C#, C++, Swift).

Instead of treating code as separate piles of data variables and functions, OOP bundles **Data (Attributes)** and the **Functions that operate on that data (Methods)** together into self-contained units called **Objects**.

```
┌────────────────────────────────────────────────────────────────────────┐
│                        ANATOMY OF AN OBJECT                            │
├────────────────────────────────────────────────────────────────────────┤
│                                                                        │
│   CLASS: `NetworkSwitch` (The Blueprint)                               │
│   ├── ATTRIBUTES (What the object KNOWS - Data State)                  │
│   │   ├── `ip_address = "192.168.1.2"`                                 │
│   │   ├── `port_count = 24`                                            │
│   │   └── `is_online = True`                                           │
│   └── METHODS (What the object DOES - Behavior)                        │
│       ├── `reboot()`                                                   │
│       ├── `enable_poe(port_number)`                                    │
│       └── `get_traffic_stats()`                                        │
│                                                                        │
│   INSTANTIATION:                                                       │
│   `core_switch = NetworkSwitch("192.168.1.2", 48)`                     │
│   `core_switch.reboot()`   <── [ Dot Notation calls method! ]          │
│                                                                        │
└────────────────────────────────────────────────────────────────────────┘
```

## 1. Classes vs. Objects: The Blueprint Analogy

- **The Class (The Architectural Blueprint):** The written code template that defines what properties every object of this type will have. You cannot live inside a paper blueprint of a house.
- **The Object (The Physical House):** A concrete, living instance built in computer RAM using the blueprint. You can build 50 completely different physical houses from the same single architectural blueprint!

```python
class Student:
    # Constructor: Initializes the object's data
    def __init__(self, name, id_number):
        self.name = name          # Attribute
        self.id_number = id_number  # Attribute
        self.credits_earned = 0   # Attribute

    # Method: An action this object can perform
    def complete_course(self, credits):
        self.credits_earned += credits

# Creating two distinct object instances from the single Student class:
student1 = Student("Marcus", "S1042")
student2 = Student("Elena", "S1043")

student1.complete_course(3)
print(student1.credits_earned)  # Outputs: 3
print(student2.credits_earned)  # Outputs: 0 (Elena's data is unaffected!)
```

## 2. The Four Pillars of Object-Oriented Programming

CompTIA tests your conceptual mastery of the four foundational pillars of OOP:

```
┌────────────────────────────────────────────────────────────────────────┐
│                        THE FOUR PILLARS OF OOP                         │
├────────────────────┬───────────────────────────────────────────────────┤
│ **1. Encapsulation**│ Hide internal variables and protect state from    │
│                    │ direct external corruption. Access via methods.   │
├────────────────────┼───────────────────────────────────────────────────┤
│ **2. Inheritance** │ Child classes inherit attributes and methods from │
│                    │ a parent class, eliminating duplicated code.      │
├────────────────────┼───────────────────────────────────────────────────┤
│ **3. Polymorphism**│ Different child classes can implement the same    │
│                    │ method in unique ways (e.g. `save()` to Cloud/SSD)│
├────────────────────┼───────────────────────────────────────────────────┤
│ **4. Abstraction** │ Hide complex inner mechanics and expose a clean,  │
│                    │ simple public interface to the user.              │
└────────────────────┴───────────────────────────────────────────────────┘
```

### Pillar 1: Encapsulation (Data Protection)
Think of a bank account object. You should not be able to directly write `account.balance = 1000000000` from outside the class! Instead, the `balance` attribute is private (encapsulated), and you must call `account.deposit(50.00)`, which validates the funds before modifying the balance.

### Pillar 2: Inheritance (Code Reusability)
You create a master parent class called `Device` with attributes `ip_address`, `mac_address`, and `hostname`.
- You can create child classes: `Printer(Device)`, `Router(Device)`, and `Workstation(Device)`.
- All three automatically inherit the networking attributes without writing those lines of code three times!

### Pillar 3: Polymorphism ("Many Forms")
Both a `PDFDocument` class and an `ExcelSpreadsheet` class can have a `.print()` method. When you call `.print()`, the PDF object executes vector rendering while the Excel object executes table grid rendering. The caller doesn't need to know the internal difference.

### Pillar 4: Abstraction (Simplicity)
When you drive a car, you press the gas pedal. You do not manually adjust the fuel injection timing, oxygen sensors, and transmission gears. The car engine **abstracts** that extreme complexity behind a simple pedal.

## Why This Matters in the Field

When you write modern automation scripts in PowerShell or Python, everything you touch is an **Object**:
- An Active Directory user returned by `Get-ADUser` is an object with `.EmailAddress`, `.Department`, and `.Enabled` attributes.
- A network socket is an object with `.Connect()` and `.Close()` methods.

Understanding OOP allows you to manipulate enterprise software APIs and automation objects with ease.
