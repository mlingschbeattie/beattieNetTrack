## Modeling the Real World in Code

In procedural programming, code is a structured list of top-to-bottom instructions. That works fine for a 20-line backup script, but when building an enterprise system with 500,000 lines of code—like an airline reservation platform or a massive cloud application—procedural code turns into an unmaintainable tangle of interdependent logic.

**Object-Oriented Programming (OOP)** is the dominant architectural paradigm used across enterprise software (Java, Python, C#, C++, Swift).

Instead of treating code as separate piles of data variables and functions, OOP bundles **Data (Attributes)** and the **Functions that operate on that data (Methods)** together into self-contained units called **Objects**.

![Object-Oriented Programming Architecture and Four Pillars Guide](/images/tech-plus/oop-architecture-four-pillars-guide.svg)

```
┌────────────────────────────────────────────────────────────────────────┐
│                        ANATOMY OF AN OBJECT                            │
├────────────────────────────────────────────────────────────────────────┤
│                                                                        │
│   CLASS: `NetworkSwitch` (The Blueprint)                               │
│   ├── ATTRIBUTES (What the object KNOWS - Data State)                  │
│   │   ├── `ip_address = "192.168.1.2"`                                 │
│   │   ├── `port_count = 24`                                            │
│   │   └── `is_online = True`                                           │
```

<Callout type="exam">
**CompTIA Tech+ Core Objective (FC0-U71 4.3):**
- **Class vs. Object:** A Class is the code template or blueprint; an Object is the concrete instance allocated in memory.
- **Attributes vs. Methods:** Attributes represent data state (`port_count`, `is_online`). Methods represent actions and operations (`reboot()`, `get_traffic_stats()`).
- **The Four Pillars:**
  1. **Encapsulation:** Protecting internal state behind private access modifiers.
  2. **Inheritance:** Child subclasses inheriting and extending parent superclass logic.
  3. **Polymorphism:** Multiple classes responding to the same method call with specialized behavior.
  4. **Abstraction:** Exposing simple public controls while hiding internal mechanics.
</Callout>

<Callout type="warn">
**Object-Oriented Operational Warnings:**
- **Exposing Raw Public State:** Making all class attributes public destroys encapsulation. Any external script can assign negative numbers to bank balances or invalid strings to IP address attributes, bypassing validation.
- **Circular Object References:** When Object A holds a reference to Object B, and Object B holds a reference back to Object A, automatic garbage collection engines may fail to free memory, causing persistent memory leaks.
- **Deep Inheritance Trees:** Over-relying on inheritance hierarchies 5 or 6 levels deep creates fragile, brittle code. Prefer composition (has-a) over inheritance (is-a) when feasible.
</Callout>

## 1. Classes vs. Objects: The Blueprint Analogy

- **The Class (The Architectural Blueprint):** The written code template that defines what properties every object of this type will have. You cannot live inside a paper blueprint of a house.
- **The Object (The Physical House):** A concrete, living instance built in computer RAM using the blueprint. You can build 50 completely different physical houses from the same single architectural blueprint!

```python
class Student:
    # Constructor: Initializes the object's data
    def __init__(self, name, id_number):
        self.name = name          # Attribute
        self.id_number = id_number  # Attribute
        self.credits_earned = 0   # Attribute

    # Method: An action this object can perform
    def complete_course(self, credits):
        self.credits_earned += credits

# Creating two distinct object instances from the single Student class:
student1 = Student("Marcus", "S1042")
student2 = Student("Elena", "S1043")

student1.complete_course(3)
print(student1.credits_earned)  # Outputs: 3
print(student2.credits_earned)  # Outputs: 0 (Elena's data is unaffected!)
```

## 2. The Four Pillars of Object-Oriented Programming

CompTIA tests your conceptual mastery of the four foundational pillars of OOP:

```
┌────────────────────────────────────────────────────────────────────────┐
│                        THE FOUR PILLARS OF OOP                         │
├────────────────────┬───────────────────────────────────────────────────┤
│ **1. Encapsulation**│ Hide internal variables and protect state from    │
│                    │ direct external corruption. Access via methods.   │
├────────────────────┼───────────────────────────────────────────────────┤
│ **2. Inheritance** │ Child classes inherit attributes and methods from │
│                    │ a parent class, eliminating duplicated code.      │
├────────────────────┼───────────────────────────────────────────────────┤
│ **3. Polymorphism**│ Different child classes can implement the same    │
│                    │ method in unique ways (e.g. `save()` to Cloud/SSD)│
├────────────────────┼───────────────────────────────────────────────────┤
│ **4. Abstraction** │ Hide complex inner mechanics and expose a clean,  │
│                    │ simple public interface to the user.              │
└────────────────────┴───────────────────────────────────────────────────┘
```

### Pillar 1: Encapsulation (Data Protection)
Think of a bank account object. External code should not be able to directly set `account.balance = 1000000000`. The `balance` attribute is private (encapsulated), requiring external callers to execute `account.deposit(50.00)`, which validates the funds before modifying the internal state.

### Pillar 2: Inheritance (Code Reusability)
You create a master parent class called `Device` with attributes `ip_address`, `mac_address`, and `hostname`.
- Child classes `Printer(Device)`, `Router(Device)`, and `Workstation(Device)` automatically inherit the networking attributes without writing those lines three times.

### Pillar 3: Polymorphism ("Many Forms")
Both a `PDFDocument` class and an `ExcelSpreadsheet` class can have a `.print()` method. When you call `.print()`, the PDF object executes vector rendering while the Excel object executes table grid rendering. The caller doesn't need to know the internal difference.

### Pillar 4: Abstraction (Simplicity)
When driving a car, you press the gas pedal. You do not manually adjust the fuel injection timing, oxygen sensors, and transmission gears. The car engine **abstracts** that extreme complexity behind a single responsive pedal.

## 3. Constructors and Object Instantiation

The **Constructor** is a special method automatically called when a new instance is created:
- In Python, it is written as `def __init__(self):`.
- In Java and C#, it shares the exact name of the class (e.g., `public Student()`).
- The constructor ensures that an object cannot exist in an uninitialized or broken state.

## 4. Access Modifiers and Data Validation Getters/Setters

To enforce Encapsulation, object-oriented languages provide **Access Modifiers**:

```
┌────────────────────────────────────────────────────────────────────────┐
│                        ACCESS MODIFIERS SUMMARY                        │
├────────────────────┬───────────────────────────────────────────────────┤
│ Modifier           │ Scope and Visibility                              │
├────────────────────┼───────────────────────────────────────────────────┤
│ **Public**         │ Accessible by any code anywhere in the project.   │
├────────────────────┼───────────────────────────────────────────────────┤
│ **Private**        │ Accessible ONLY inside the declaring class itself.│
├────────────────────┼───────────────────────────────────────────────────┤
│ **Protected**      │ Accessible within the declaring class and its     │
│                    │ inherited child subclasses.                       │
└────────────────────┴───────────────────────────────────────────────────┘
```

### Why Use Getters and Setters?
By marking attributes private and providing public **Getter** and **Setter** methods, you retain complete control over validation:

```python
class BankAccount:
    def __init__(self, owner, initial_balance):
        self.owner = owner
        self._balance = initial_balance  # Private attribute

    # Getter: Controlled read access
    def get_balance(self):
        return self._balance

    # Setter: Validation gatekeeper
    def set_balance(self, amount):
        if amount < 0:
            raise ValueError("Error: Account balance cannot be negative!")
        self._balance = amount
```

If code attempts to assign a negative balance, the setter rejects it immediately, protecting corporate data integrity.

## Why This Matters in the Field

When writing automation scripts in PowerShell or Python, everything you interact with is an **Object**:
- An Active Directory user returned by `Get-ADUser` is an object with `.EmailAddress`, `.Department`, and `.Enabled` attributes.
- A network socket is an object with `.Connect()` and `.Close()` methods.

Understanding OOP allows you to manipulate enterprise software APIs and automation objects with confidence and precision.
