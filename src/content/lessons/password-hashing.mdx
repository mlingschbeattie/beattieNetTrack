## Assume the Database Is Already Stolen

That is the mindset password storage is designed around. Not "how do we keep attackers out" — that is a different set of controls. The question here is narrower and darker: the attacker has your entire users table sitting on their laptop right now. How much damage can they do with it?

If the passwords are plaintext, the answer is total. Every account on your system is compromised, and because people reuse passwords, so are those users' email, banking, and school accounts. That is the breach that ends companies.

The reason hashing solves this is that a login server never actually needs to know your password. It only needs to answer one question: does the string this person just typed match the one they registered with? A one-way hash answers that perfectly. Store the digest at registration, hash the attempt at login, compare the two. The original is never written down, so there is nothing in the database to steal.

The demo below hashes whatever you type across several algorithms at once. Type the same word twice and the digests are identical — that determinism is what makes verification possible, and it is also the property an attacker exploits.

## The Problem With a Plain Hash

Determinism cuts both ways. If `password123` always produces the same SHA-256 digest, an attacker does not have to crack anything — they precompute the digests of every common password once, then look up your stolen hashes in that table. That is a **rainbow table**, and against unsalted hashes it turns cracking into a search.

Worse, identical passwords produce identical rows. An attacker scanning a stolen database sees that four hundred accounts share one digest and immediately knows those four hundred people all chose the same password. Crack it once, own all of them.

## What the Salt Fixes

A **salt** is a random value generated per user and mixed into the password before hashing. It is stored in plaintext right next to the hash, and that is fine — a salt is not a secret. Its job is to make every hash unique.

Now the same password produces a different digest for every user, because every user has a different salt. The precomputed table is worthless: the attacker would have to build a fresh rainbow table for each individual salt, which defeats the entire point of precomputation. Identical passwords no longer look identical. Cracking becomes a per-user problem instead of a bulk one.

Note carefully what salting does *not* do. It does not make any single password harder to guess. An attacker targeting one account still takes that user's salt, appends candidate passwords, and hashes away. Salt removes the shortcut. It does not slow the long road.

<Callout type="exam">
Keep the two defenses separate in your head, because CompTIA writes questions that hinge on the difference. Salt defeats precomputation — rainbow tables and identical-hash correlation. A slow algorithm with a work factor defeats brute force. A system needs both, and neither substitutes for the other.
</Callout>

## Slow on Purpose

SHA-256 was designed to be fast, because file integrity checking needs speed. That design goal is exactly wrong for passwords. A single modern GPU tries billions of SHA-256 candidates per second, so a salted SHA-256 hash of a weak password still falls in minutes.

The fix is an algorithm built to be slow. **bcrypt**, **scrypt**, and **Argon2** all take a tunable **work factor** — a cost parameter that controls how much computation each hash requires. Set it so a single login takes roughly 100 to 250 milliseconds. A user never notices a quarter second. An attacker trying to test billions of candidates now needs billions of quarter-seconds, and the economics collapse.

Because the cost is a parameter rather than a property of the algorithm, you raise it as hardware improves. The same bcrypt code you deploy today stays viable for a decade; you just increment the work factor every few years.

**Argon2** goes one step further and consumes a configurable amount of memory per hash. GPUs get their cracking advantage from running thousands of tiny parallel cores, and those cores have very little memory each. Force every hash to allocate real memory and that parallelism evaporates. Argon2id is the current recommendation for new systems; bcrypt remains perfectly acceptable and is far more widely supported.

<Callout type="warn">
The response that makes things worse is reaching for more layers instead of the right algorithm. Hashing SHA-256 a thousand times in a homemade loop, or chaining MD5 into SHA-1 into SHA-256, feels like added effort and buys almost nothing — you have built a slow hash with none of the analysis behind bcrypt, and you have probably introduced a bug that weakens it. The other version of this mistake is treating a breach as a hashing problem when the passwords were fine: if users reused credentials leaked elsewhere, no work factor helps, because the attacker is logging in with the correct password. That is credential stuffing, and it is answered with MFA and breach-password screening, not a better hash.
</Callout>

## Why This Matters

You will meet this as a code review, an audit finding, or an incident. Someone will show you a users table and ask whether it is acceptable, and you need to answer in three checks: is it hashed rather than encrypted or plaintext, is there a unique per-user salt, and is the algorithm deliberately slow with a sane work factor. If any one of those is missing, the finding writes itself. And when a breach does happen, the storage format is what determines whether you are sending a routine notification or watching every one of your users get taken over.

## Ethical Use

Password cracking tools and techniques belong in systems you own or are contracted in writing to test. Running them against accounts, databases, or hashes that are not yours is a criminal offense in most jurisdictions, regardless of intent.
