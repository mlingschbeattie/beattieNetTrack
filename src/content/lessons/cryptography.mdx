## Three Words People Use Interchangeably and Shouldn't

Somebody hands you a string that looks like gibberish and says it is encrypted. Maybe it is. Maybe it is Base64, which is not encryption at all and takes about two seconds to reverse. Maybe it is a SHA-256 digest, which nobody reverses ever. These are three separate operations with three separate purposes, and confusing them is how secrets end up in public repositories.

**Encoding** changes the representation of data so a system can transport it safely. Base64 turns binary into text that survives an email header. Hex turns bytes into readable pairs. There is no key and no secret — encoding is a translation anyone can undo. If you see `=` padding at the end of a string, you are almost certainly looking at Base64, and it is protecting nothing.

**Encryption** turns readable data into ciphertext using a key, and turns it back with a key. The point is that it is reversible for the person holding the key and useless to everyone else. Confidentiality is the goal.

**Hashing** takes any input and produces a fixed-length digest — and there is no way back. That one-way property is the feature. It is how a system checks your password without storing it, and how you prove a 4 GB disk image was not modified by comparing 64 hex characters.

## Symmetric and Asymmetric — Why Every Real Protocol Uses Both

**Symmetric encryption** uses one key for both directions. AES is the standard, and it is fast — a modern CPU has dedicated instructions for it and encrypts gigabytes per second. The problem is delivery. If you and I both need the same key, how does it get from you to me across a network an attacker is already watching?

**Asymmetric encryption** solves exactly that. You hold a key pair: a public key you hand out freely and a private key you never share. Anything encrypted with the public key can only be decrypted with the private key. Now I can encrypt something for you without ever having met you. The trade-off is speed — RSA is orders of magnitude slower than AES and can only encrypt small amounts of data.

So protocols use both. TLS opens with an asymmetric handshake whose only job is to agree on a shared symmetric key. Once both sides hold that key, the connection switches to AES for everything else. Asymmetric crypto for the introduction, symmetric crypto for the conversation.

Signatures invert the key usage. You sign with your **private** key, and anyone verifies with your **public** key. That direction is what makes a signature meaningful — only you could have produced it, and verification proves both who sent the data and that it was not modified in transit.

<Callout type="exam">
Know the direction of every key operation cold. Encrypt for someone: their public key. Decrypt what you received: your private key. Sign something: your private key. Verify a signature: the sender's public key. Security+ tests this as a scenario, not a definition — you get a situation and have to pick the key.
</Callout>

## Where Cryptography Actually Breaks

Almost nobody breaks AES. The math holds. Breaches come from everything around the math.

**Keys in the wrong place.** A hardcoded key in source code, a key committed to a repository, a key in an environment variable that an error page dumps to the browser. The cipher is fine. The key is public.

**Broken primitives still in production.** MD5 and SHA-1 are collision-broken — an attacker can construct two different inputs that produce the same digest, which destroys their use for integrity. DES has a 56-bit key that falls to brute force. Both still appear in old code, and both still show up on exams as the wrong answer.

**Confidentiality mistaken for integrity.** This is the subtle one. Encrypting data hides it. It does not stop someone from *changing* it. With a mode like AES-CBC and no authentication tag, an attacker who cannot read your ciphertext can still flip bits in it and cause it to decrypt into different plaintext. That is why authenticated modes like AES-GCM exist — they encrypt and authenticate in one operation, so tampering is detected instead of silently accepted.

<Callout type="warn">
The response that makes things worse is stacking a second layer of the same broken thing. Hashing a password twice with MD5 does not fix MD5, and re-encrypting an encrypted blob under the same reused key adds no security while doubling the code that can fail. When a primitive is broken, replace it — do not layer it. The same instinct produces "encrypt then hash then encode," which reads as thorough and defends against nothing.
</Callout>

## Why This Matters

Cryptography shows up in every security role, and almost never as "implement a cipher." You will be asked why a certificate warning appeared, whether a stored password format is acceptable, which algorithm a legacy system uses and whether it has to be replaced, and how a key gets rotated without breaking every client. Those are all questions about the edges. Get the vocabulary exact and the key directions automatic, and the rest of the security curriculum — TLS, PKI, VPNs, signed updates, disk encryption — becomes a set of applications of the same handful of ideas.

## Ethical Use

Everything on this page is for understanding and defending systems you own or have written authorization to test. Decoding, cracking, or tampering with data belonging to anyone else is illegal regardless of how easy the tooling makes it look.
