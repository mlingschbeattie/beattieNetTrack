## Trusting What the Screen Says

Imagine signing into your online banking portal. You see an account balance of \$5,000.

Now consider what happens if an unauthorized intruder compromises the financial database. The adversary does not exfiltrate your account numbers—instead, they subtly alter database triggers so that whenever you initiate a \$50 utility payment, the processing engine debits \$500 instead.

In this scenario, confidentiality remains intact (no unauthorized third party read your balance), and availability is unaffected (the banking web application responds promptly). Yet the entire computational infrastructure is compromised because **you cannot trust the accuracy or validity of the data**.

**Integrity** is the essential "I" within the **CIA Triad**. It is the absolute guarantee that digital data remains unaltered, complete, and uncorrupted throughout its lifecycle—protecting against malicious software injections, rogue insiders, network bit rot, and unintended administrative errors.

## 2. Cryptographic Hashing: The Mathematical Seal

A **Cryptographic Hash Function** is a one-way mathematical algorithm that ingests arbitrary binary payloads (from a 10-byte plaintext string to a 100-gigabyte disk image) and produces a fixed-length hexadecimal digest:

1. **One-Way Function (Pre-image Resistance):** It is trivial to calculate a hash from a given input, but computationally impossible to reverse-engineer the original source payload from the resulting hash digest.
2. **Deterministic Output:** Supplying identical binary input on any computing platform globally will consistently generate the exact same hash output.
3. **The Avalanche Effect:** Altering a single bit in an enterprise disk image causes more than 50% of the bits in the resulting hash digest to change unpredictably.

```
┌────────────────────────────────────────────────────────────────────────┐
│                      HASH ALGORITHM COMPARISON                         │
├──────────────┬───────────────┬─────────────────────────────────────────┤
│ Algorithm    │ Digest Length │ Cryptographic Security Status           │
├──────────────┼───────────────┼─────────────────────────────────────────┤
│ MD5          │ 128 Bits      │ BROKEN (Vulnerable to collision attacks)│
│ SHA-1        │ 160 Bits      │ DEPRECATED (Banned for digital certs)   │
│ SHA-256      │ 256 Bits      │ CURRENT INDUSTRY GOLD STANDARD          │
│ SHA-3        │ 256–512 Bits  │ Modern sponge-construction standard     │
└──────────────┴───────────────┴─────────────────────────────────────────┘
```

<Callout type="exam">
**CompTIA Exam Focus — Hash Comparison Verification:** When an operating system vendor releases an ISO installation file (e.g., `server-2025.iso`), the vendor publishes the official SHA-256 checksum on their verified portal. After downloading, an administrator runs `Get-FileHash -Algorithm SHA256 .\server-2025.iso` in PowerShell. If the calculated digest matches the published string character-for-character, the administrator verifies that the image was neither damaged during transmission nor tampered with by a malicious intermediary.
</Callout>

<Callout type="warn">
**The MD5 Collision Hazard:** Legacy hashing functions such as MD5 and SHA-1 suffer from **collision vulnerabilities**. In a collision attack, an adversary crafts two entirely distinct files (one benign, one malicious) that compute to the identical MD5 digest. Never rely on MD5 or SHA-1 for security integrity verification or digital signatures.
</Callout>

## 3. Digital Signatures: Combining Integrity with Authentication

While a cryptographic hash proves whether a file has changed, it cannot prove *who produced it*. An attacker could modify a script and simply generate a new hash.

A **Digital Signature** integrates hashing with **Asymmetric Public-Key Cryptography** to deliver non-repudiation and origin verification:
1. The software vendor generates a cryptographic hash of their compiled binary.
2. The vendor encrypts the hash using their securely guarded **Private Key**.
3. When client endpoints download the package, the operating system decrypts the digital signature using the vendor's verified **Public Key** embedded in the trusted root certificate store.
4. The endpoint independently computes a hash of the downloaded binary. If the two values match, the system confirms two foundational facts:
   - **Integrity Verified:** The binary has not been modified since the developer signed it.
   - **Origin Authenticated:** Only the possessor of the vendor's private key could have authored the signature.

## 4. File Integrity Monitoring (FIM) and Tamper-Evident Storage

In production server deployments, organizations implement automated continuous monitoring to protect critical system states:

### File Integrity Monitoring (FIM)
Tools such as Tripwire, Wazuh, and OSSEC baseline the cryptographic hashes of core operating system files (`/etc/passwd`, `C:\Windows\System32\drivers\etc\hosts`, registry hives):
- Background agents scan system files at scheduled intervals or upon write events.
- If a malware persistence mechanism or rogue administrator alters a system DLL, FIM immediately flags the hash divergence, alerts the Security Operations Center (SOC), and triggers automated rollback procedures.

### Tamper-Evident Logging and WORM Media
When adversaries compromise a server, their primary operational priority is clearing event logs (`wevtutil cl System` or `rm /var/log/auth.log`) to hinder digital forensics.
- **WORM Storage:** Write Once, Read Many physical media and cloud object locks prevent records from being modified or overwritten for a mandated retention window.
- **Hash-Chained Audit Logs:** Each new log entry incorporates the hash of the preceding entry. Modifying an entry midway through the file breaks the cryptographic chain across all subsequent records, providing irrefutable mathematical evidence of log tampering.

## Why This Matters in the Field

Systems engineers and incident responders rely on integrity mechanisms across several critical workflows:
1. **Malware Attribution:** Comparing suspect executable hashes against the VirusTotal database to identify known ransomware variants.
2. **Chain of Custody:** Generating SHA-256 disk image hashes immediately upon seizing evidence at a crime scene to prove in court that digital artifacts remained unaltered during analysis.
3. **Supply Chain Defense:** Validating cryptographically signed software bills of materials (SBOMs) to ensure open-source software dependencies have not been hijacked.
